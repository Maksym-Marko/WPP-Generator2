# CLAUDE.md — WPPG-NEXT base template

Instructions for Claude (and developers) **maintaining this repository itself**.
If you are working inside a *generated* plugin, read `example.CLAUDE.md` instead.

This file stays small on purpose. Detailed, per-feature instructions live in
`.claude/rules/` and load automatically when you open a matching file. Use the
**Feature map** below to open the right rule *before* investigating or changing a
feature. (The rules are also loaded on demand via their `paths:` frontmatter —
you do not need `@`-imports here.)

## What this repository is

This is the **reusable WordPress plugin starter template** consumed by the
**WPPG-NEXT converter** (https://wppg-next.markomaksym.com.ua/). The converter
takes this code as its source, swaps a fixed set of placeholder tokens for a
user's plugin name / prefix / author details, and emits a ready-to-use plugin
zip. **Preserve the starter features** — do not delete working examples (custom
table, REST, Gutenberg blocks, React app, meta boxes, Next.js headless endpoints)
when maintaining.

The converter itself is **not in this checkout** — it lives one directory up at
`../wpp-generator-next-wrapper/` (source of truth `raw-wppg-code/`). The bundled
headless frontend lives under `next-js/`. `example.CLAUDE.md` and
`example.cursorrules` are templates shipped *to* generated plugins, not rules for
this repo.

## ⚠️ Placeholder protection rule (read before any rename)

The converter does **blind, case-sensitive `str_replace` on file contents and on
file/dir paths**. Any occurrence of these exact tokens — even inside a larger
identifier — is replaced. They must keep their **exact spelling, casing,
punctuation, and location**. Before changing, moving, renaming, or removing any
occurrence, **stop and ask the user**, showing the exact value, file, proposed
change, and converter impact. Continue unrelated work while waiting.

| Exact token in this repo | Becomes (final plugin) | Where it appears |
|---|---|---|
| `MXSFWN` | unique prefix, UPPERCASE | PHP constants (`MXSFWN_PLUGIN_*`), namespace root `MXSFWNWPPGNext`, composer PSR-4 |
| `mxsfwn` | unique prefix, lowercase | `MXSFWN_PLUGIN_UNIQUE_STRING` value, block names (`mxsfwn/…`), block category, handles, composer name |
| `This Plugin Name` | plugin display name | `wpp-generator-next.php` header, `readme.txt` title |
| `This Plugin Author` | author name | `wpp-generator-next.php` header |
| `wpp-generator-next` | text domain / main file / folder slug | text domain everywhere, `wpp-generator-next.php` filename, paths, `block.json` `textdomain` |
| `_markomaksym_` | contributors | `readme.txt` `Contributors:` line (underscores, not asterisks) |
| `Brief description` | short description | plugin header, `readme.txt` |
| `Long description` | long description | plugin header, `readme.txt` |
| `https://markomaksym.com.ua/wp-plugin-skeleton-generator/` | Plugin URI | plugin header |
| `https://github.com/Maksym-Marko` | Author URI | plugin header |

Notes: the main filename `wpp-generator-next.php` is renamed to
`<text-domain>.php`; any `wpp-generator-next` path segment becomes the folder
slug. Because replacement is substring-based, do **not** introduce new strings
that contain `mxsfwn` / `MXSFWN` / `wpp-generator-next` as a coincidental
substring unless you intend them to be rewritten, and never invent a second
prefix.

## Entry points (brief)

`wpp-generator-next.php` (header, constants, PHP ≥ 8.4 guard, requires) →
`index.php` (boots `MXSFWNWPPGNext\WppGenerator`) → three feature hubs:
`Admin\AdminSoul`, `Frontend\FrontendSoul`, `Features\FeaturesSoul`. Lifecycle via
`install.php` / `uninstall.php`. Full detail:
`.claude/rules/plugin-structure.md`.

## Setup / build commands (verified: PHP 8.4.3, Composer 2.10.3, npm 11.4.2)

```bash
composer install            # PHP deps + autoloader
composer dump-autoload      # after adding/moving PHP classes
npm install                 # JS toolchain
npm run start               # watch: tailwind + gutenberg + native JS
npm run build               # production build of all three bundles
```

Build pipeline detail (what owns which source/output, auto-discovery, Tailwind
caveats): `.claude/rules/frontend-build.md`. The headless app in `next-js/` has
its **own** `package.json` and commands: `.claude/rules/nextjs-headless.md`.

- **No active lint/format/test scripts** and no PHPUnit config. Lint on demand:
  `npx wp-scripts lint-js`, `npx wp-scripts lint-style`, `npx wp-scripts format`.
- `node generate-structure.js` regenerates `plugin-structure.md` (docs only).

## Shared conventions

- **Never hand-edit `build/`** — it is compiled output, regenerated by the build
  commands. Edit sources in `src/` / `assets/` and recompile.
- One PSR-4 class per file under `includes/` (namespace `MXSFWNWPPGNext\`); run
  `composer dump-autoload` after adding one. Start every directly-reachable PHP
  file with `defined('ABSPATH') || exit;`. Match existing spacing/docblock style.
- Do not reorganize folders or rename files casually — paths containing
  `wpp-generator-next` are load-bearing for the converter. Ask before creating
  new top-level files/folders.
- **Security (required for all new code)**: validate + sanitize input; escape on
  output for the context (`esc_html`/`esc_attr`/`esc_url`/`esc_textarea`/
  `wp_kses_post`); `$wpdb->prepare()` for every dynamic value and whitelist
  column/`ORDER BY` names; nonce + capability check on every write; use
  `wp_safe_redirect(wp_validate_redirect(...))`. Treat the shipped examples as
  **structure references, not a security baseline** — several under-escape; audit
  them yourself.

## Validating a template change

1. `composer dump-autoload` (if PHP classes changed) and `npm run build`.
2. Confirm no placeholder token was altered unintentionally:
   `grep -rn "MXSFWN\|mxsfwn\|wpp-generator-next\|This Plugin Name\|This Plugin Author\|_markomaksym_" --include=*.php --include=*.json --include=*.txt .`
3. Activate in the local WordPress (this repo lives under a working install at
   `app/public`): activation runs the table migration, the "WPPG Next" / "AI
   robots" menus appear, blocks show under the "WPPG Next" category, and REST
   routes answer under `/wp-json/wpp-generator/v1/…`. Check `debug.log`.

In a **freshly generated plugin** (requires converter access at
`../wpp-generator-next-wrapper/`): run "Regenerate Plugin input", generate with a
sample name/prefix, and confirm the prefix/namespace/text-domain/filename were
rewritten consistently and the plugin activates cleanly.

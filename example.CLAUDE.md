# CLAUDE.md

Copy this file to the root of your plugin as `CLAUDE.md`. It tells Claude Code
how this plugin is laid out, how to build it, and how to extend it safely.

The plugin was generated by **WPPG-NEXT**: your plugin name, prefix, namespace,
text domain, and main-file name are already baked into the code and into every
identifier used below, so the names in this guide match your checkout exactly.

Detailed, per-feature instructions live in `.claude/rules/` and load
automatically when you open a matching file. The **Feature map** at the bottom
links each one — open the matching rule *before* changing a feature. Manual-only
references (not auto-loaded) live in `.claude/guides/`.

## Architecture & where things load

- Main file `wpp-generator-next.php` — plugin header, constants
  (`MXSFWN_PLUGIN_VERSION`, `MXSFWN_PLUGIN_PATH/_URL/_BASE_NAME/_ABS_PATH`,
  `MXSFWN_PLUGIN_UNIQUE_STRING` = `mxsfwn`). On `PHP >= 8.4` it requires
  `vendor/autoload.php`, `includes/Shared/functions.php`, `install.php`,
  `index.php`.
- `index.php` boots `MXSFWNWPPGNext\WppGenerator`, which constructs three feature
  hubs ("souls"):
  - `includes/Admin/AdminSoul.php` — admin pages, admin assets, CPT, taxonomy,
    meta boxes, list tables.
  - `includes/Frontend/FrontendSoul.php` — frontend assets, shortcodes.
  - `includes/Features/FeaturesSoul.php` — Gutenberg blocks, REST routes.
- Lifecycle: `install.php` registers `Activator`/`Deactivator`; `uninstall.php`
  runs `Uninstall::init()`. Full detail: `.claude/rules/plugin-structure.md`.

## Shared conventions

- **One PSR-4 class per file** under `includes/`, namespace root
  `MXSFWNWPPGNext\` (see `composer.json`). Run `composer dump-autoload` after
  adding or moving a class. Start every directly-reachable PHP file with
  `defined('ABSPATH') || exit;`. Match the surrounding spacing/docblock style.
- Shared helpers live in `includes/Shared/functions.php`, prefixed `mxsfwn`
  (`mxsfwnView`, `mxsfwnRequireFrontendComponent`, …).
- **Never hand-edit `build/`** — it is compiled output, regenerated by the build
  commands. Edit sources in `src/` / `assets/` and recompile
  (`.claude/rules/frontend-build.md`).
- Keep the plugin's own identifiers consistent: PHP prefix `MXSFWN`/`mxsfwn`,
  namespace `MXSFWNWPPGNext\`, block names `mxsfwn/<slug>`, block category
  `mxsfwn-wppgnext`, text domain `wpp-generator-next`. Don't invent a second
  prefix.
- **Security (required for all new code)**: validate + sanitize input; escape on
  output for the context (`esc_html`/`esc_attr`/`esc_url`/`esc_textarea`/
  `wp_kses_post`); use `$wpdb->prepare()` for every dynamic value and whitelist
  column/`ORDER BY` names; add a nonce + capability check to every write; redirect
  with `wp_safe_redirect(wp_validate_redirect(...))`. The shipped examples are
  **structure references, not a security baseline** — a few under-escape, so audit
  any example you copy and apply these rules to all new code.

## Workflows

### 1. Set up this plugin ("WPPG setup" / "Generator setup")

Treat "WPPG install", "WPPG setup", "Generator setup", or "set up this starter
kit" as a request to install dependencies. First confirm you are in the plugin
root: `composer.json` has the `MXSFWNWPPGNext\\` PSR-4 autoload and `package.json`
has the `start`/`build` scripts. Then, from the plugin root:

```bash
composer install   # PHP deps + autoloader
npm install        # JS toolchain
```

If a command fails, report the exact command and the blocker.

After the dependency installs, offer optional Git setup. Ask the user: "Would you
like me to initialize a Git repository for this plugin and set up its
`.gitignore`?"

- **If yes**, run `git init` from the plugin root (if the folder is already a Git
  repository, reuse it rather than re-initializing). Once Git is ready, rename
  `example.gitignore` to `.gitignore`. If `.gitignore` already exists, leave both
  files in place and tell the user. If `git init` fails, report the error and
  leave `example.gitignore` untouched.
- **If no**, finish setup without running `git init` or renaming the file.

Report the dependency-install results and the Git-setup results separately. Leave
the headless app in `next-js/` alone unless the user also asks for it — it has its
own dependencies (workflow 3).

### 2. Explain the features ("What can WPPG do?")

For "what can WPPG do?", "tell me about the features", and similar, give a short,
grouped overview of the kit's verified capabilities (admin & data examples,
frontend tooling, Gutenberg, REST API, Next.js). The full inventory —
distinguishing working examples from extension patterns — is in
**`.claude/guides/features.md`**; read it and summarize rather than guessing. Note
that AJAX is a documented pattern only, not a pre-built example.

### 3. Work on the bundled Next.js app

For "I want to create a Next.js application" (or similar), start from the existing
`next-js/` App Router app — don't scaffold a new one. Read its `package.json`
scripts, `example.env`, and `app/services/` REST client first, then:

```bash
cd next-js
npm install
```

Check the installed versions against the latest available and report which
dependencies are outdated, which updates are worth taking, and which would be a
major-version migration (e.g. Next/React). If you can't reach the registry, say
which versions you could verify. Apply upgrades only if the user asks.

Trace how the app fetches pages and navigation and renders Gutenberg content
through the plugin's public REST routes, and reuse those contracts. If the
requested behavior isn't covered, name the gap before proposing a new endpoint or
architecture change. Detail: `.claude/rules/nextjs-headless.md`.

### 4. Follow this plugin's conventions

Before adding or editing a feature: open its rule (feature map below) and inspect
the closest existing example. Use the plugin's actual namespace
(`MXSFWNWPPGNext\…`), naming, and registration pattern. Put PHP classes,
JavaScript, and CSS alongside comparable code in the existing admin / frontend /
Gutenberg structure, register the feature from the matching soul, work in `src/`,
and regenerate compiled assets with the build scripts.

## Build & verify

```bash
composer dump-autoload   # after adding/moving PHP classes
npm run build            # rebuild all JS/CSS before testing (npm run start = watch)
```

There is no bundled test suite or active lint script; lint on demand with
`npx wp-scripts lint-js` / `npx wp-scripts lint-style`. Verify changes in a local
WordPress: activate the plugin, exercise the admin pages / blocks / REST routes
you touched, and confirm no PHP notices in `debug.log`.

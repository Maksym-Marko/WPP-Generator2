# CLAUDE.md

Copy this file to the **root of your generated plugin** as `CLAUDE.md`. It is
addressed to Claude working **inside a plugin generated by the WPPG-NEXT
generator**. (It does not cover maintaining the generator template itself.)

## First: resolve this plugin's identifiers

The generator rewrote the template's placeholder tokens into your plugin's own
names. Before editing, detect them from the checkout — do not assume
`mxsfwn`/`MXSFWN`/`wpp-generator-next`:

- **Main file + text domain + folder slug**: the single `*.php` in the root that
  carries the `Plugin Name:` header. Its filename (minus `.php`) is your **text
  domain** and folder slug; use it in `__()/_e()` calls and asset paths.
- **PHP prefix / namespace**: open the main file — constants are
  `<PREFIX>_PLUGIN_VERSION`, `<PREFIX>_PLUGIN_ABS_PATH`, etc.; the Composer PSR-4
  root in `composer.json` is `<Prefix>WPPGNext\\` → `includes/`. The lowercase
  prefix is the value of `<PREFIX>_PLUGIN_UNIQUE_STRING` and prefixes asset
  handles, block names (`<prefix>/block-name`), and the block category.

Find them quickly (run from the plugin root):

```bash
grep -oE "define\('[A-Z0-9]+_PLUGIN_UNIQUE_STRING', '[^']+'" *.php   # lowercase prefix
grep -n "psr-4" -A2 composer.json                                    # namespace root
ls *.php                                                             # main file = text domain
```

Throughout this file, `<PREFIX>` = uppercase PHP prefix, `<prefix>` = lowercase
prefix, `<text-domain>` = main-file slug. **Directory layout below survives
generation unchanged** (`includes/`, `src/`, `build/`); only the main `.php`
filename and the prefix/text-domain strings differ.

## Architecture & where things load

- Main file (`<text-domain>.php`) defines constants, then on `PHP >= 8.4` loads
  `vendor/autoload.php`, `includes/Shared/functions.php`, `install.php`,
  `index.php`.
- `index.php` boots `<Prefix>WPPGNext\WppGenerator`, which constructs three hubs:
  - `includes/Admin/AdminSoul.php` — admin pages, admin assets, CPT, taxonomy,
    meta boxes.
  - `includes/Frontend/FrontendSoul.php` — frontend assets, shortcodes.
  - `includes/Features/FeaturesSoul.php` — Gutenberg blocks, REST routes.
- Lifecycle: `install.php` registers `Activator`/`Deactivator`; `uninstall.php`
  runs `Uninstall::init()`.

## PHP conventions

- One PSR-4 class per file under `includes/` in namespace `<Prefix>WPPGNext\…`.
  Run `composer dump-autoload` after adding a class.
- Start every directly-reachable PHP file with `defined('ABSPATH') || exit;`.
- **Admin vs frontend separation**: admin-only code under `includes/Admin/`
  (controllers, views, entities, utilities); frontend under `includes/Frontend/`;
  shared/feature code under `includes/Features/` and `includes/Shared/`. Register
  new admin behavior from `AdminSoul`, frontend from `FrontendSoul`, blocks/REST
  from `FeaturesSoul`.
- Helpers in `includes/Shared/functions.php` are prefixed (`<prefix>View`,
  `<prefix>RequireFrontendComponent`, …).

## Admin menus, submenus & page routing

Edit `includes/Admin/routes.php`. Use the fluent router:

```php
$router->get('my-controller')                 // file in includes/Admin/controllers/
    ->menuAction('addSubmenuPage')             // addMenuPage|addSubmenuPage|addOptionsPage|addOptionLink
    ->properties([
        'parentSlug' => 'wppg-next',
        'pageTitle'  => 'My Page',
        'menuTitle'  => 'My Page',
        'menuSlug'   => 'my-page',
        'capability' => 'manage_options',      // default; tighten/loosen deliberately
    ]);
$router->route();                              // already called at file end
```

- **Controller**: `includes/Admin/controllers/my-controller.php` — runs on page
  load; render a view with `<prefix>View('my-view', [ 'foo' => $bar ])`.
- **View**: `includes/Admin/views/my-view.view.php`.
- **Capability** is enforced by WordPress at the menu level via the `capability`
  property; still re-check inside the controller for any state-changing action.
- **Page-specific assets**: enqueue in `includes/Admin/Utilities/
  AdminEnqueueScripts.php`, gating on the current screen/`$_GET['page']` so you
  don't load everywhere.

## Gutenberg blocks & block extensions

- Each block is a folder in `src/gutenberg/<name>/` with `block.json`,
  `index.js`, `edit.js`, `save.js`, and optional `style.css`/`editor.css`.
  Register the folder by importing it in `src/gutenberg/index.js`.
- Registration is automatic: `includes/Features/Gutenberg/CustomBlocks.php`
  globs `src/gutenberg/*/block.json` and calls
  `register_block_type_from_metadata()`. In `block.json`, `name` is
  `<prefix>/<slug>` and `category` is `<prefix>-wppgnext` — keep that prefix.
- **Dynamic (SSR) blocks**: add `"render": "file:./render.php"` to `block.json`
  and create `render.php` (see `src/gutenberg/ssr-simple/`). `$attributes` is in
  scope; wrap markup with `get_block_wrapper_attributes()` and **escape every
  attribute you print** (`esc_html`, `esc_attr`, `esc_url`).
- **Block extensions** (e.g. `src/gutenberg/highlight-extending/`) add filters/JS
  only, no `save`. Build: `npm run gutenberg-js:build` → `build/blocks/blocks.js`;
  editor assets are enqueued by `CustomBlocks::enqueueBlocks()`.

## JavaScript / CSS: edit vs regenerate

**Edit sources in `src/`; never hand-edit `build/`.** `build/` is compiled
output only — it is regenerated by the build commands, so any manual edit there
is silently overwritten on the next build. **Before working on any CSS or JS,
open the config file that owns that pipeline first** to confirm the
input/output paths and naming conventions:

| Source (edit) | Config to read first | Command | Output (enqueued) |
|---|---|---|---|
| `assets/css/style.css` (+ Tailwind in `src/**`) | `postcss.config.js`, `tailwind.config.js` | `npm run tailwind-css:build` | `build/css/style.css` |
| `src/gutenberg/**` | `webpack.gutenberg.config.js` | `npm run gutenberg-js:build` | `build/blocks/*` |
| `src/admin/**`, `src/frontend/**` | **`webpack.custom.config.js`** | `npm run native-js:build` | `build/admin/*`, `build/frontend/*`, `build/dependencies/vendors/*` |

- `webpack.custom.config.js` **auto-discovers one entry per subdirectory** of
  `src/admin/` and `src/frontend/` (excluding `gutenberg`); each subfolder must
  contain an `index.js`. SCSS is extracted to `build/<area>/<feature>/index.css`
  **only if it is imported from that `index.js`**. So to add page-specific CSS:
  create `src/admin/<feature>/index.js` that imports
  `./assets/scss/style.scss` (copy `src/admin/meta-box-image-upload/`), run the
  build, then enqueue the compiled `build/admin/<feature>/index.css` in
  `AdminEnqueueScripts.php` gated on `$_GET['page']`.
- Tailwind's `content` globs scan only `src/**`, **not** `includes/**` — utility
  classes added to admin views/controllers are not generated. Style view markup
  with real CSS rules (via a `src/` entry as above), or extend
  `tailwind.config.js` `content` to include the view path.

`npm run start` watches all three; `npm run build` does a production build.
Enqueueing: admin bundles in `includes/Admin/Utilities/AdminEnqueueScripts.php`,
frontend bundles (React app, Font Awesome, Tailwind) in
`includes/Frontend/Utilities/WPEnqueueScripts.php`. Handles are prefixed with
`<prefix>` and versioned by `<PREFIX>_PLUGIN_VERSION`. The React frontend app
lives in `src/frontend/react-js/` and is mounted via the
`[react_js_app_short_code]` shortcode. Note: the template enqueues the React app
on *all* frontend pages — gate it to the pages that need it.

## Existing patterns to copy

- **Settings page**: `includes/Admin/views/settings-menu.view.php` +
  `settings-menu` controller (registered via `addOptionsPage`/`addOptionLink` in
  `routes.php`). For real options use the WordPress Settings API
  (`register_setting`, nonce'd `options.php` forms).
- **Shortcodes**: add methods to `includes/Frontend/Utilities/ShortCodeGenerator.php`.
- **CPT / taxonomy**: `PostTypeGenerator` / `TaxonomyGenerator` in
  `includes/Admin/Utilities/`, invoked from `AdminSoul`.
- **Meta boxes**: `MetaBoxGenerator::addPageMetaBoxes()` with typed views under
  `includes/Admin/views/meta-boxes/`; image meta uses the REST route +
  `src/admin/meta-box-image-upload/`.
- **REST endpoints**: create a class extending
  `includes/Features/API/AbstractClasses/AbstractRestRouteHandler.php`, set
  `$route`/`$methods`, implement `handleRequest()`, and register the instance in
  `includes/Features/API/init.php`. Namespace is `wpp-generator/v1` → consumed at
  `/wp-json/wpp-generator/v1/…`.
- **Custom DB table**: migration pattern in `includes/Activate/` (run from
  `Activator`); list-table UI in `includes/Admin/Utilities/Tables/`.
- **Database changes**: do schema work in an activation migration
  (`includes/Activate/`), guarded with `CREATE TABLE IF NOT EXISTS` /
  version-option checks; add matching cleanup to `includes/Uninstall.php`.

## Security conventions for new code (required)

- **Capabilities**: check `current_user_can()` for the *specific* object where
  possible (`current_user_can('edit_post', $postId)`), not just a generic cap.
- **Nonces**: every form/AJAX/state-changing admin action needs a nonce
  (`wp_create_nonce` / `wp_verify_nonce`, or `check_admin_referer`). For REST,
  rely on the cookie nonce (`X-WP-Nonce`) and a real `permission_callback` — a
  permission callback that `return true` makes the route fully public, so only
  use it for intentionally public reads.
- **Input**: validate type/shape, then sanitize (`sanitize_text_field`,
  `sanitize_textarea_field`, `sanitize_key`, `absint`, `sanitize_title`, …).
  Remember `sanitize_text_field` does **not** remove quotes.
- **Output**: escape at the point of output for the context —
  `esc_html`, `esc_attr`, `esc_url`, `esc_textarea`, `wp_kses_post`. Do **not**
  assume input sanitization makes output safe.
- **Database**: always `$wpdb->prepare()` for any value in a query; for ORDER BY /
  column / table names (which `prepare` can't bind) **whitelist** against a known
  list. Never interpolate `$_GET`/`$_POST` into SQL.
- **Redirects**: use `wp_safe_redirect( wp_validate_redirect( $url, $fallback ) );
  exit;` — never echo `window.location` from a request value or
  `$_SERVER['HTTP_REFERER']`.

> The template ships example code to learn the structure from, but **treat its
> escaping/query handling as a reference, not a security baseline** — audit any
> example independently (the custom-table list view and the `<prefix>GoBack`
> helper under-escape) and apply the rules above to all new code.

## Build & verify checklist

```bash
composer dump-autoload   # after adding/moving PHP classes
npm run build            # rebuild all JS/CSS before testing
```
There is no bundled test suite or active lint script; lint on demand with
`npx wp-scripts lint-js` / `npx wp-scripts lint-style`. Verify changes in a local
WordPress: activate the plugin, exercise the admin pages/blocks/REST routes you
touched, and confirm no PHP notices in `debug.log`.
